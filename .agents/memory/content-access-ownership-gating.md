name: Content-access ownership gating
description: How ownership-gated nav + Blitz server enforcement works — funnel product group, boot-seeded map defaults, fail-closed middleware semantics.
---

- Registry `MAPPABLE_PRODUCTS` now has a third group `"funnel"` (the 4 YSE upsells incl. `yse_21_day_blitz`). Funnel columns are plain checkboxes in the admin matrix — they do NOT participate in mentorship copy-upward propagation. The admin UI (`ContentAccessMap.tsx`) and `admin-panel-api.ts` `ContentAccessProduct.group` union must stay in lockstep with the registry union.
- `content_access_map` defaults are boot-seeded (`seed-content-access-map.ts`, wired in app.ts) with INSERT … ON CONFLICT (page_key) DO NOTHING — **admin edits always win; never convert this to an upsert**. Policy: `blitz` → yse_21_day_blitz + 5 tiers; `partner-tools`/`prime-corporate`/`ad-credit`/`become-a-coach` → 5 mentorship tiers only (LaunchPad+, per owner decision 2026-08-04); everything else → 6 front-ends + 5 tiers. `vip` deliberately excluded everywhere.
- **Why fail-closed middleware double-checks the row**: `getAccessiblePageKeys` treats a missing map row as OPEN (nav launch semantics). `requirePageAccess` (used by all Blitz APIs) therefore also verifies the row EXISTS and denies members when it doesn't (admins/coaches pass) — otherwise a failed/late boot seed silently opens gated content.
- Nav-stricter-than-route is deliberate for pitch items (Private Coaching / Accountability Partner / Concierge hidden behind `coaching:group`; pages stay reachable by direct link and pitch). Such cases must be declared in `NAV_ONLY_GATING` in `member-nav-vs-route-gating.test.ts` or the drift guard fails.
- Adding a new GATEABLE_PAGES key ⇒ also decide its default slugs in `defaultSlugsForPageKey` and rebuild the registry dist (`tsc -b lib/content-access-registry --force`).
- **Blitz guide HTML must never ship in the client bundle.** `BLITZ_BODY_HTML` is deliberately NOT exported from the @workspace/blitz-curriculum barrel (subpath exports `./blitz-body-html` + `./blitz-video-map` are server-only); the portal fetches it from gated `GET /blitz/guide` (`useBlitzGuideHtml` in Blitz.tsx, reused by VideoReview) and the archived copy from admin-only `GET /admin/blitz-archive-guide`. **Why:** any barrel re-export or portal import re-leaks paid content to non-owners via static JS. Verify with a `version-banner`/`vb-tag` grep of the vite dist after related changes.
- The legacy `course-progress` routes also enforce Blitz ownership via `hasPageAccessForUser` (the express-free core of requirePageAccess): POST/DELETE with any Blitz course id (v2, legacy `blitz-hub-step-N`, `21-day-blitz`) → 403; GET filters Blitz rows for non-owners instead of 403 because it's a mixed endpoint that must keep serving quick-start etc.
- `blitz-page-access.test.ts` briefly deletes + restores the shared dev DB's `blitz` map row (fail-closed test); don't run it in parallel with other content-access suites, and the boot seed self-heals if a run is interrupted. Program not launched as of Aug 2026 ⇒ hard enforcement, no grandfathering.
- **KB ownership gate (owner_page_key)**: `ai_live_documents.owner_page_key` (+ same column on kb_staging_docs; push-approved copies it with COALESCE preserve-if-null so a NULL draft never un-gates a live doc) gates retrieval data-driven. `retrieveSurfaceAware` takes `access: {viewerUserId} | "internal" | omitted(=fail-closed)`, applied to ALL FOUR SQL paths (nav grounding, precise, semantic, loose fallback). Chat passes the viewer and also ownership-gates the fuzzy Blitz section-pointer blocks; internal review tooling (self-test, corpus sweep, admin coverage search) uses "internal"; voice omits (fail-closed, operations-only anyway). Boot migration re-stamps blitz corpora (`blitz_section IS NOT NULL` live rows, `blitz_section_import` staging rows) every boot. A new gated corpus = stamp its docs' owner_page_key; zero retrieval code change. Tests: `kb-ownership-filter.test.ts` (shared dev DB, throwaway users only).
